Laya

A multilingual, non-autoregressive decision engine. It reads a text and a set of typed questions, then returns one probability distribution per question from a single encoder pass. It writes no free text.

421M / 322MModernBERT-large (EN) / mmBERT-base (multilingual)
512–8,192tokens of context, depending on checkpoint
33 msone question on a T4 (upstream figure)
~1 GBmemory; runs on CPU, CUDA or Apple MPS

Source: the blog post "Laya: a local System 1 decision model", the upstream README, and a reading of laya/common.py and laya/agent.py in our clone at upstream/laya.

What it does

Laya handles "System 1" decisions: fast, typed judgements over a piece of text, where you would otherwise prompt a chat model and parse its answer. There are three question types, shared with TypeSafe's System One API:

TypeCriteriaReturnsTypical use
nouloptional texts for true / falseP(yes)"Does the note document ≥20 pack-years?"
choicenamed options with descriptionsdistribution over options, top option, confidencerouting, intent, category
scoreordered levelsdistribution over levels, expected levelurgency, severity

Architecture

  • Encoder. The encoder is bidirectional, so the option markers can attend to the whole note and the note can attend to the question.
  • Head. A question-type embedding is added to every token, then a 2-layer pre-norm transformer runs over the sequence. An MLP scorer reads each marker's hidden state and gives one logit per option. A small "act" head reads entropy and margin features. Upstream says it carries no usable signal yet (issue #185).
  • Router. laya.Router detects the script and language in under 1 ms, in pure Python, and sends non-English text to the multilingual checkpoint. It exists because the English checkpoint is confidently wrong on other scripts: Khmer scores 0.000 at 0.952 confidence.

Training: RLCD

Laya is trained with reinforcement learning against strictly proper scoring rules, which upstream calls RLCD. For each question the trainer draws G = 4 noisy logit vectors around the model's output. It scores each one with a reward that combines log, spherical and ranked-probability scores (proper_reward), then takes a GRPO-style policy-gradient step on the group-normalised advantage, plus a soft cross-entropy term. Proper scoring rules reward reporting the true probability, and that is the argument for calibration. After training, one temperature per question type is fitted with LBFGS on a held-out slice.

Upstream's own numbers: on typed-decisions (2,000 decisions), the base English checkpoint scores 0.362 zero-shot, below the 0.461 majority baseline. The fine-tuned checkpoint scores 0.766 (Jev: 0.727). XNLI English scores 0.860. After temperature refitting, ECE falls from 0.466 to 0.081.

What upstream says about its limits, and why it matters here. "Laya is a fast base to specialise, not a zero-shot decision engine." The English noul can follow its false/true label text instead of the state (issue #156). Negation is unsafe (#377). The shipped checkpoints are over-confident, and laya-multilingual has no fitted temperatures. For clinical checklists, this predicts weak zero-shot results and makes the fine-tuning experiment essential. Our results confirm both points.

Running it locally

uv venv --python 3.13 upstream/laya/.venv
uv pip install --python upstream/laya/.venv/bin/python -e "upstream/laya[serve]"

from laya import Router
router = Router(device="mps")            # Apple GPU; "cuda" or "cpu" also work
r = router.predict(note_text, {
    "lcs_age": {"type": "noul", "instructions": "Is the patient between 50 and 80 years old, inclusive?"},
})
r["answers"]["lcs_age"]["noul"]          # P(yes)

Other entry points: the laya CLI, laya-serve (a Jev-compatible HTTP server), an MCP server, LangChain tools, ONNX export, a TileLang CUDA fast path, and prediction hooks for PII redaction and audit logging.
